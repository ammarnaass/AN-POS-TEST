# تحليل معماري شامل: واجهة تسجيل الدخول والاقتران وتداخل المودالات والشاشات

> **تاريخ التقرير:** 19 سبتمبر 2026  
> **النظام:** AN POS Mobile (React Native 0.87 + React Navigation 7 + Nitro Modules)  
> **الملفات المستهدفة:** `LoginScreen.tsx`، `PairScreen.tsx`، `ModeSelectScreen.tsx`، `authStore.ts`، `apiClient.ts`، `App.tsx`

---

## 1. الملخص التنفيذي (Executive Summary)

يعاني مسار المصادقة (Auth & Pairing Flow) في التطبيق من تداخل حاد بين النوافذ المنبثقة (Modals) والشاشات، وارتباك في إدارة حالات الاتصال وتراجع التنقل (Back Navigation)، خصوصاً عند تسجيل الحساب أو الانتقال بين الوضع المتصل (Connected LAN) والمستقل (Standalone).

بعد فحص دقيق للكود المصدري، تبيّن أن المشكلة ليست مجرد خطأ في التنسيق البصري، بل ناتجة عن **5 عيوب معمارية وهيكلية مترابطة**:

1. **تراكب وتصادم 3 مودالات متزامنة في شاشة الاقتران (`PairScreen.tsx`)**.
2. **غياب معالج زر الرجوع (`BackHandler`) عند تسجيل الحساب في (`LoginScreen.tsx`)**.
3. **الخلط الكارثي بين "تسجيل خروج المستخدم" و"فك اقتران الجهاز" في (`authStore.ts`)**.
4. **تخبط حزمة التنقل (Navigation Stack) بسبب الاستخدام غير المتسق لـ `replace` و `navigate`**.
5. **ارتباك الواجهة في حالة انقطاع السيرفر أو البدء لأول مرة بدون مستخدمين**.

## 2. التشخيص المعماري المفصل للمشاكل (Root Causes)

### المشكلة الأولى: فوضى وتصادم المودالات في شاشة الاقتران (`PairScreen.tsx`)

#### أين تقع المشكلة في الكود؟
تعتمد شاشة الاقتران `PairScreen.tsx` على **ثلاثة مودالات متزامنة**:
1. **مودال تأكيد الاقتران وإدخال PIN الستة أرقام:**  
   `PairScreen.tsx:1406`: `<Modal visible={pairModalVisible}>`
2. **مودال كاميرا مسح الباركود المستقل:**  
   `DesktopPairingScanner.tsx:294`: `<Modal visible statusBarTranslucent>`
3. **مودال شاشة الاتصال والتحقق ذات الرسوم المتحركة:**  
   `PairScreen.tsx:1556`: `<Modal visible={connectStage !== 'idle'}>`

#### الأثر الفني (Technical Impact):
- في نظام أندرويد (`Android WindowManager`)، لا يدعم محرك React Native الأصلي فتح عدة نوافذ `Modal` في آن واحد. عندما يُفتح مودال جديد أثناء محاولة إغلاق أو رسم مودال آخر، تحدث المشاكل التالية:
  - فقدان استجابة اللمس تماماً (`Touch Event Swallowing`).
  - تجمد النافذة أو ظهور شاشة سوداء.
  - بقاء طبقة التعتيم الخلفية (`Backdrop`) عالقة في واجهة المستخدم حتى بعد انتهاء العملية.
- حاول الكود وضع ترقيع يدوي ([PairScreen.tsx#L288](file:///home/ammar/AN-POS-TEST/mobile-rn/src/features/pair/PairScreen.tsx#L288)):
  ```typescript
  // Dismiss modal if open so modals don't overlap in Android
  if (fromModal) {
    setPairModalVisible(false);
  }
  setScannerVisible(true);
  ```
  ثم إعادة فتحه في `onClose` و `onScanned`. هذا التبديل اللحظي غير مستقر ويسبب سباق حالات (`Race Conditions`) بسبب التأخر الطبيعي في دورة حياة المكونات الأصلية (Unmount Latency).

### المشكلة الثانية: عطب الرجوع أثناء تسجيل الحساب (`LoginScreen.tsx`)

#### أين تقع المشكلة في الكود؟
- في `LoginScreen.tsx:46-64`: وضع "إنشاء حساب" ليس شاشة تنقل مستقلة، بل مجرد تبديل حالة محلية:
  ```typescript
  type ViewMode = 'login' | 'register';
  const [view, setView] = useState<ViewMode>('login');
  ```
- **غياب معالج `BackHandler` لأجهزة أندرويد**:
  عندما يكون المستخدم في وضع التسجيل (`view === 'register'`) ويضغط على زر الرجوع الفعلي أو إيماءة الرجوع في هاتفه:
  - لا يفهم النظام أنه يريد العودة إلى شاشة تسجيل الدخول (`view = 'login'`).
  - يقوم محرك التنقل فوراً باستدعاء `navigation.goBack()`.
  - ولأن شاشة `Login` يتم الدخول إليها غالباً عبر `navigation.replace('Login')` من شاشات `Bootstrap` أو `ModeSelect`، فإن الضغط على الرجوع يتسبب في **الخروج المفاجئ من التطبيق تماماً وإغلاقه**، أو الرجوع العشوائي لشاشة قديمة وفقدان كافة البيانات المدخلة في الحقول!
- **غياب زر رجوع في الـ Header**:
  لا يوجد في أعلى نموذج التسجيل أي سهم رجوع واضح، والوسيلة الوحيدة المتاحة هي رابط نصي صغير في أسفل النموذج الطويل بعد التمرير (`لديك حساب بالفعل؟ تسجيل الدخول`).

### المشكلة الثالثة: الخلط الكارثي بين "تسجيل الخروج" و"فك الاقتران"

#### أين تقع المشكلة في الكود؟
في ملف [authStore.ts#L60-L71](file:///home/ammar/AN-POS-TEST/mobile-rn/src/store/authStore.ts#L60-L71):
```typescript
logout: async () => {
  const user = get().user;
  if (user?.id) {
    electronAPI.auth.logout(user.id).catch(() => {});
  }

  try {
    const currentMode = await getStoredMode();
    const isConnected = currentMode === 'connected' || session.isConnectedSync();

    if (isConnected) {
      await session.unpair(); // ⚠️ خطأ فادح: تسجيل خروج المستخدم يقوم بفك اقتران الجهاز بالكامل!
    } else {
      await AnposSecureStore.remove(STORAGE_KEYS.USER_ID);
    }
  } catch (err) { ... }
}
```
كما تكرر هذا الخلط الصريح في رسائل التأكيد بملفي `HomeLayout.tsx` و `HomeTabs.tsx`:
> *"هل أنت متأكد من رغبتك في تسجيل الخروج؟ سيتم إلغاء الربط مع الحاسوب مباشرة والعودة للوضع المستقل."*

#### الأثر الفني والتشغيلي (Operational Impact):
- **المفهوم التشغيلي الصحيح في نقاط البيع**:
  - **تسجيل الخروج (User Logout):** إجراء متكرر يومياً لإنهاء وردية كاشير ليدخل كاشير آخر مكانه، ويجب أن **يبقى التابلت متصلاً بالحاسوب والسيرفر المركزي**.
  - **فك الاقتران (Device Unpairing):** إجراء إداري استثنائي يتم من شاشة الإعدادات لإلغاء ربط التابلت بالسيرفر.
- **ما يحدث حالياً:** بمجرد أن يضغط أي كاشير على "تسجيل الخروج":
  1. يتم مسح توكن الاقتران `SESSION_TOKEN`.
  2. يتم مسح معرّف الجهاز `DEVICE_ID`.
  3. يتم مسح رابط السيرفر `SERVER_URL`.
  4. يتم استدعاء `removePairedDevice()` وحذف بيانات الربط.
  5. يتم تحويل قاعدة البيانات قسراً إلى الوضع المستقل `unifiedDB.switchToStandalone()`.
- **النتيجة:** يعود التابلت إلى شاشة الدخول وهو غير متصل (Offline/Standalone)، ويعتقد المستخدم أن الاتصال انقطع فجأة وتحدث فوضى واختلاط كامل بين الوضعين!

### المشكلة الرابعة: تخبط حزمة التنقل وحلقات الشاشات المفتوحة (Navigation Loops)

#### أين تقع المشكلة في الكود؟
التطبيق يعاني من تضارب في إدارة الحزمة بين `replace` و `navigate`:
```
BootstrapScreen
  ├── replace('ModeSelect')
  └── replace('Login')

ModeSelectScreen
  ├── (الوضع المستقل)  ──> replace('Login')
  └── (الربط بالحاسوب) ──> navigate('Pair')

LoginScreen
  ├── (شارة الوضع)     ──> navigate('ModeSelect')  ⚠️ يضع ModeSelect فوق Login
  └── (تغيير نقطة البيع)──> navigate('Pair')        ⚠️ يضع Pair فوق Login

PairScreen
  ├── (الوضع المستقل)  ──> replace('Login')         ⚠️ يبدّل Pair بـ Login فوق Login السابقة!
  └── (نجاح الاتصال)   ──> replace('Login')
```

#### الأثر الفني:
1. إذا كان المستخدم في `Login` وضغط على شارة الوضع، يذهب إلى `ModeSelect`، ثم يختار الوضع المستقل فيقوم بعمل `replace('Login')`. تصبح حزمة التنقل تحتوي على: `[Login -> Login]`.
2. عند الضغط على زر الرجوع في الهاتف، يرجع إلى شاشة `Login` السابقة بدلاً من الخروج، مما يعطي إحساساً بأن الشاشة علقت أو تكررت.
3. في شاشة `PairScreen` وشاشة `ModeSelectScreen`، **لا توجد أزرار رجوع في الـ Header** للعودة إلى شاشة تسجيل الدخول بطريقة طبيعية.

### المشكلة الخامسة: اختلاط الواجهة عند انقطاع السيرفر أو البدء لأول مرة

#### 1. عند البدء لأول مرة في الوضع المستقل (First Run):
- في `BootstrapScreen.tsx:106`: إذا كان الوضع مستقلاً وعدد المستخدمين 0، يتم توجيه المستخدم إلى `ModeSelectScreen`.
- إذا اختار المستخدم "الوضع المستقل"، يتم تحويله إلى `LoginScreen`.
- لكن في `LoginScreen`، تبدأ الشاشة في وضع تسجيل الدخول `view = 'login'` بحقول فارغة وتطلب اسم مستخدم ورمز PIN، مع أن قاعدة البيانات فارغة تماماً ولا يوجد أي مستخدم!
- المستخدم الجديد يصاب بالحيرة: "ماذا أكتب وأنا لم أسجل حساباً بعد؟". زر إنشاء الحساب صغير جداً في الأسفل، وكود الإنشاء التلقائي للأدمن ينتظر من المستخدم تخمين كتابة `admin` و `1234`!

#### 2. عند تعطل سيرفر الحاسوب في الوضع المتصل:
- عند فتح التطبيق مع وجود اقتران سابق وسيرفر غير متصل، تفشل محاولة تسجيل الدخول وتظهر رسالة "السيرفر غير متصل".
- في الوضع المتصل، يتم إخفاء زر "إنشاء حساب" تماماً (`mode === 'standalone' && ...`).
- لا يتاح للمستخدم خيار سريع وواضح:
  - "العمل في الوضع المستقل (Offline Mode)"
  - أو "إعادة فحص الاتصال"
  - أو "تعديل عنوان السيرفر".
- يضطر المستخدم للخروج والبحث العشوائي بين شاشات الاقتران واختيار الوضع.

  4. **إبقاء `serverUrl` وبيانات الاقتران وقاعدة البيانات كما هي**.
- **الملفات التابعة:** [HomeLayout.tsx](file:///home/ammar/AN-POS-TEST/mobile-rn/src/components/HomeLayout.tsx) و [HomeTabs.tsx](file:///home/ammar/AN-POS-TEST/mobile-rn/src/components/HomeTabs.tsx) و [StoreSettingsScreen.tsx](file:///home/ammar/AN-POS-TEST/mobile-rn/src/features/settings/StoreSettingsScreen.tsx):

### الخطوة 2: إصلاح شاشة تسجيل الدخول والتسجيل (`LoginScreen.tsx`)
- **الملف:** [src/features/auth/LoginScreen.tsx](file:///home/ammar/AN-POS-TEST/mobile-rn/src/features/auth/LoginScreen.tsx)
- **الإجراءات المطلوبة:**
  1. **إضافة `BackHandler` للتعامل مع زر الرجوع في أندرويد**:
     - إذا كان `view === 'register'`، يقوم زر الرجوع بالتبديل إلى `view = 'login'` ويمنع خروج التطبيق (`return true`).
     - إذا كان `view === 'login'` وجاء المستخدم من `ModeSelect`، يسمح بالرجوع الطبيعي.
  2. **إضافة زر رجوع مرئي في شريط العنوان (Header)**:
     - عند التواجد في وضع "تسجيل الحساب"، يظهر سهم رجوع واضح في أعلى الشاشة يعيد المستخدم فوراً إلى واجهة تسجيل الدخول.
     - وضع زر رجوع/تغيير الوضع بشكل بارز وليس مجرد شارة ملونة.
  3. **التحويل التلقائي عند أول تشغيل (Auto-switch on First Run)**:
     - إذا كان التطبيق في الوضع المستقل وعدد المستخدمين 0 (`db.users.count() === 0`)، يتم ضبط `view = 'register'` تلقائياً مع عرض شارة ترحيبية: *"مرحباً بك! يرجى إنشاء حساب المدير للبدء"*.
  4. **معالجة انقطاع السيرفر بمرونة (Offline Recovery)**:
     - عند فشل الاتصال بالسيرفر في الوضع المتصل، يظهر زر سريع: *"التحويل إلى الوضع المستقل"* أو *"إعادة محاولة الاتصال"*.

### الخطوة 3: توحيد وهيكلة مودالات شاشة الاقتران (`PairScreen.tsx`)
- **الملف:** [src/features/pair/PairScreen.tsx](file:///home/ammar/AN-POS-TEST/mobile-rn/src/features/pair/PairScreen.tsx)
- **الإجراءات المطلوبة:**
  1. **منع التداخل بين المودالات (Prevent Modal Collision)**:
     - استخدام آلة حالة موحدة (`PairingModalState = 'none' | 'pin_code' | 'camera_scanner' | 'connecting' | 'success'`).
     - لا يتم فتح مودال الكاميرا أو مودال شاشة الاتصال إلا بعد التأكد من إغلاق المودال السابق بالكامل عبر `onDismiss` أو بعد انتهاء تأثير الخروج.
  2. **إضافة زر رجوع قياسي في الـ Header**:
     - إضافة زر رجوع في أعلى يمين/يسار الشاشة يعيد المستخدم إلى الشاشة السابقة (`navigation.goBack()`).
  3. **تنظيف الانتقال النهائي**:
     - إغلاق كافة المودالات والرسوم المتحركة أولاً قبل استدعاء `navigation.replace('Login')`.

### الخطوة 4: تنظيف مسارات التنقل في التطبيق (`App.tsx` و `ModeSelectScreen.tsx`)
- اعتماد استراتيجية تنقل منضبطة:
  - التحويل بين وضع الدخول والتسجيل يكون داخلياً داخل `LoginScreen` عبر الـ State مع دعم كامل لـ `BackHandler`.
  - الانتقال إلى `PairScreen` أو `ModeSelectScreen` يكون عبر `navigate` مع وجود زر رجوع في الـ Header.
  - عند نجاح الاقتران أو التبديل للوضع المستقل، يتم استخدام `navigation.reset` بحزمة نظيفة تحتوي فقط على `Login`، لمنع تراكم الشاشات في الذاكرة.

## 5. مصفوفة التحقق والاختبار (Verification Checklist)

| السيناريو المراد اختباره | السلوك المتوقع بعد الإصلاح |
